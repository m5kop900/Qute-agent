## M5 live check (10 minutes, needs a real OpenCode 2 server and a model that can call tools)
Run `ctest` first (new tests: `tst_agentstate`, `tst_clientparse`). Then with `qute` open, send these prompts and watch the sprite + panel:
1. "Run `ls` in the project" -> `thinking` -> `working` (detail `bash`) -> `done` -> `idle`. If the tool needs permission: `waiting` with Allow/Always/Deny.
2. Press **Allow**: the sprite must leave `waiting` immediately and the tool must run. Press **Deny** on another: the turn must end, no hang.
3. Prompt that makes the model ask a question (forms): `waiting` + text "opencode asks: ...", **Cancel question** resumes.
4. Press **Stop** during a long answer: state goes to `idle` (not `done`/`error`).
5. Kill the server (`pkill -f "opencode serve"` or stop it) -> `offline` within ~5 s; start it again -> back to `idle` without restarting qute.
6. Optional: a prompt that spawns a sub-agent (task tool) that needs permission -> the overlay must still show `waiting` (child session).
If any step fails, copy the raw SSE events of that turn (`curl -N -u opencode:PASSWORD http://127.0.0.1:4096/api/event`) into a bug note; the fix is usually one line in `AgentState::handleEvent`.

**M5c (optional clean-up):** delete the V1 branches in `OpenCodeClient`/`AgentState` and their tests once V2 is verified; V2 is the target.

# Part 2 — Feature roadmap (F0–F7)

M0–M8 above are the foundation (build, window, daemon, connection, state machine, packs, packaging). Part 2 turns Qute into a
practical everyday interface for OpenCode 2: input, modes/models/context, conversation, session integration, auto compaction,
mascot polish, settings. Source: the "Qute Agent — Feature Roadmap & Implementation Specification" (Nov 16, 2026). Every requirement of
that specification is kept below as a checkbox; nothing was dropped.

## How to work on Part 2 (rules from the specification)
1. **Audit before coding.** Each phase starts with the "Audit" note below, then you re-check the code (it may have changed).
2. **Incremental.** One task = one small commit. Never implement a whole phase in one change.
3. **No rewrites of working subsystems** without a concrete technical reason written in the commit message.
4. **Separation:** UI (QML) / OpenCode integration (`OpenCodeClient`, new services) / session state (new `SessionStore`) / app logic (`OverlayController`, `AppConfig`).
5. **Prefer native OpenCode** APIs and CLI. No own summarizer, no own mode logic, no hardcoded model lists, no own history store.
6. **No new dependencies** unless unavoidable (decide in writing). Keep Linux + Wayland working; keep it lightweight.
7. **Errors are explicit** (visible message + log), never silent.
8. **Tests** for important functionality (`ctest`, mock server where a real one is needed) and **docs updated in the same commit**.
9. **Definition of Done:** a feature is done only when (a) its automated tests pass, (b) its live check passes against a real OpenCode 2 server,
   (c) docs are updated. *A visible UI element alone never counts.* Mark tasks `[x]` only with evidence (commit id + what was run).
10. API paths below marked **(verify)** come from upstream docs/tests, not from a live server. Confirm with the server's `/openapi.json` first.

## Dependency map and recommended order
```
M5 live check (finish) ─┐
F0 foundations ─────────┼─► F1 input ─► F4 session integration
 (SessionStore,         ├─► F2 modes/models/context ─► F5 auto compact
  catalog service,      ├─► F3 conversation UI
  layout skeleton)      └─► F6 mascot ; F7 settings (parallel, mostly independent)
```
Suggested order: **M5 live check -> F0 -> F4.1 (cheap, high value) -> F1 -> F2 -> F3 -> F5 -> F6 -> F7.**
The specification lists phases 1..7 by priority; F0 is NOT in it but is an *architectural dependency* found during the audit:
today the client only keeps one string (`responseText`), the overlay only the last answer, and the layout has no room for
attachments, selectors or a context ring. Building those features on top of that would force rework in every phase.
